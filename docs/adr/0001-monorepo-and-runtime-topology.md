# ADR 0001: Monorepo and runtime topology

- Status: Accepted; partially superseded by
  [ADR 0007](0007-shared-modular-monolith-and-generated-contracts.md)
- Date: 2026-07-14
- Deciders: Engineering

## Context

Rezumi has a server-rendered/product web application, a typed HTTP API,
long-running and security-sensitive document/AI/render work, reusable UI and wire
contracts, and local PostgreSQL/Redis/object dependencies. The repository began
empty. A foundation is needed that gives one reproducible developer entry point
without collapsing independently scalable/security-sensitive processes together.

## Decision

Use a production-oriented monorepo with these runtime applications:

- `frontend/web`: Node.js 24, pnpm 11.13.0, Next.js 16.2.11 App Router, React 19.2.7,
  TypeScript 5.9.3, and Tailwind CSS 4.3.2;
- `backend/api`: Python 3.13/uv 0.11.21, FastAPI 0.138.2, Pydantic, async
  SQLAlchemy/asyncpg, and Alembic infrastructure;
- `backend/worker`: Python 3.13/uv 0.11.21 and Celery 5.6.3;
- PostgreSQL with pgvector, Redis, and MinIO in local Docker Compose.

Use a single pnpm workspace lockfile for JavaScript and committed uv lockfiles for
the independently deployable Python projects. OpenAPI generated by FastAPI is the
wire-contract authority; generated TypeScript contracts will live in
`shared/contracts`. `frontend/ui`, `frontend/eslint-config`, `frontend/typescript-config`,
and `frontend/test-fixtures` have narrow responsibilities documented in `AGENTS.md`.

Docker Compose is the supported local integration path. It is not a production
deployment design. Production topology, managed services, regions, and queue
durability are decided with measured requirements before Phase 10.

## Consequences

### Positive

- One repository can change API, generated contract, UI, worker, infrastructure,
  docs, and tests atomically.
- API and worker can scale and receive network/resource policy independently.
- Pinned toolchains and container-first setup reduce host-specific drift.
- Provider/domain boundaries remain testable without third-party credentials.

### Costs and risks

- Two language ecosystems require disciplined lockfile, CI, and dependency
  management.
- Shared code can become an accidental coupling point; packages need explicit
  ownership and dependency direction.
- Redis is appropriate for local Celery foundation but does not settle production
  broker durability.
- A Compose-green build does not prove production security, scale, or recovery.

## Alternatives considered

- **Single Next.js application with server actions and direct persistence:** fewer
  services, but poor isolation for Python parsing/AI/rendering and weaker OpenAPI
  boundary.
- **Python-rendered monolith:** simpler backend deployment, but does not match the
  required Next.js interaction/design stack and still needs isolated jobs.
- **Independent repositories:** stronger release separation, but high early
  contract/version coordination cost for a small team and greenfield product.
- **Kubernetes in Phase 0:** premature operational surface without production
  scale/regional requirements.

## Verification

Phase 0 proves the choice with `make setup`, `make dev`, healthy web/API/worker/
PostgreSQL/Redis/MinIO, committed locks, and repository format/lint/type/test
gates. Later production claims require a separate deployment ADR and failure/load/
restore evidence.
